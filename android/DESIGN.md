# WaveTagger Rec for Android (ネイティブ録音 + WebView) 設計案

改訂: 2026-10-25 初版 / 2026-10-26 レビューを反映 (§10)。**未実装** (コードは検証用 `android/StereoTest` のみ)

## 1. 目的と前提

- S21 (SC-51B, Android 15) の内蔵マイク 2 個 (約 14.25cm 間隔、本体の下端寄り `builtin_mic_1` と上端寄り `builtin_mic_2`) を、`AudioRecord` の入力元 `MIC` でステレオ録音する。ブラウザ (Chrome/Firefox) は通話・音声用の経路でマイクを渡すため、左右が同じ音になる
- **実測で確認済み (2026-10-25)**:
  - `MIC` / `CAMCORDER` は左右が別の音。`UNPROCESSED` / `VOICE_RECOGNITION` / `VOICE_COMMUNICATION` は下端のマイク 1 個だけで、左右が完全に同一
  - 左右の時間差が ±19〜23 サンプル (0.40〜0.48ms) に張り付く = 2 個のマイクの間隔 (0.416ms) と一致。左端/右端を交互に叩くと符号が入れ替わる (`Tools/analyse_stereo.py` で Drive に届いた 3 本の WAV を分析)
  - **中身の精度は 16bit**: float32 で受け取っても、全サンプルの 99% で 24bit の下位 8 ビットが 0 (端末側が 16bit で、変換しているだけ)
  - `MIC` / `CAMCORDER` では「経路」「使われているマイク」(`routedDevice` / `activeMicrophones`) が取れない。2 個のマイクが使われていることは時間差から確かめた (API の報告では確かめられない)
- 録音以外は、今の `docs/` の画面 (タブ・メーター・LUFS・ステレオスコープ・相関・履歴・設定) をそのまま使う。**画面と測定の実装は 1 本のまま** (`docs/` が正本。ブラウザ版も引き続き使える)
- PC 側 (Inbox が `pcm録音/_Inbox` を監視 → Raw に取り込み) は変更しない。出力は 24bit/48kHz/ステレオの WAV (中身は 16bit 精度)

## 2. 全体の形

```
┌─────────────── Android アプリ (jp.wavetagger.rec) ───────────────┐
│  MainActivity ─ WebView ─ assets/web/ (docs/ のコピー)           │
│        ▲  JS → ネイティブ: WTNativeBridge (JavaScriptInterface)  │
│        │  ネイティブ → JS: 音のブロック (ArrayBuffer) と状態 (JSON)│
│  RecordService (前面サービス, type=microphone)                    │
│     AudioRecord(MIC, float32, ステレオ, 48kHz) ──┬─ ブロックを画面へ │
│        録音全体の値 (ピーク・無音・Integrated)    ├─ (画面が前の時だけ)│
│                                                 └─ 24bit WAV 書込 │
│  UploadWorker (WorkManager) ── Google 認可 ── Drive 再開可能 PUT  │
└───────────────────────────────────────────────────────────────────┘
```

- **画面 (JS) が持つもの**: UI、レベルメーター、Momentary / Short-term LUFS (`loudness.js`)、スコープ・相関 (`scope.js`)、履歴の表示
- **ネイティブが持つもの**: マイクの取り込み、WAV ファイル、**録音全体に関わる値** (ピーク・無音判定・Integrated LUFS: 画面を消している間も数える)、送信待ちと Drive への送信、Google の認可、設定 (§4)
- 音のブロックは今のワークレットと**同じ形** (`[Float32Array L, Float32Array R]`、2048 フレーム前後) で JS に渡す。**画面が裏に回ったら (`onPause`) 送るのを止める** (WebView の JS は止まるので、送り続けると溜まってメモリを圧迫し、戻った時にまとめて流れ込む)

## 3. プロジェクト構成

- 新規 `android/WaveTaggerRec/` (Kotlin、minSdk 29 / target 34、`jp.wavetagger.rec`)。検証用 `android/StereoTest` は残す
- 依存: `androidx.webkit` (WebViewAssetLoader、ArrayBuffer のメッセージ)、`androidx.work` (送信待ちの再試行)、`com.google.android.gms:play-services-auth` (Drive の認可)。AppCompat / Compose は使わない
- **画面ファイルは `docs/` から自動コピー**: Gradle のタスクで `docs/` の `index.html` `app.js` `wav.js` `loudness.js` `scope.js` (+ `native.js`) を `assets/web/` に入れる。`sw.js` / `manifest` / `worklet.js` は入れない
- 画面の配信は `WebViewAssetLoader` (`https://appassets.androidplatform.net/assets/web/index.html`)。安全なオリジンなので `localStorage` が使え、`file://` の制限を避けられる
- **橋のセキュリティ**: 橋 (`WTNativeBridge`) は WebView に読み込まれたページなら呼べてしまう。同梱のページ以外への移動は禁止 (`shouldOverrideUrlLoading`)、外部リンクは端末のブラウザで開く
- **回転で作り直さない**: `configChanges="orientation|screenSize|screenLayout|keyboardHidden"`。それでも作り直された時 (メモリ不足など) のために、ページは開くたびにサービスへ今の状態 (録音中か・経過時間) を聞いて表示を戻す
- ビルド: 検証用と同じ (JDK 20 + Gradle 8.6 + AGP 8.3.2)。出力 APK を Drive の `pcm録音` に置く (Inbox が拾わないよう `_Inbox` の外。試験後は消す)

## 4. JS ↔ ネイティブの橋 (`WTNativeBridge`)

`docs/native.js` が `window.WTNativeBridge` の有無を見て、`window.WTNative` を作る。無ければ (ブラウザ) 今までどおり。

**JS → ネイティブ** (JSON の文字列で受け渡し、結果はイベントで返す)

| 呼び出し | 働き |
|---|---|
| `getState()` | 録音中か・経過時間・入力元・送信待ちの数・認可の状態 (ページを開いた時に必ず呼ぶ) |
| `open()` / `close()` | マイクを開く (前面サービス開始) / 閉じる。戻り: チャンネル数・レート・左右の入れ替え有無・無効にできたエフェクト |
| `startRecording()` / `stopRecording()` | WAV の書き出しの開始/終了。終了の戻り: ファイル名・秒数・ピーク・Integrated・無音かどうか |
| `listRecordings()` | 履歴 (名前・秒数・形式・送信状態・失敗理由) |
| `upload()` / `connect()` | 送信待ちを送る / Google の認可 (初回と同意切れの時だけ画面が出る) |
| `getSettings()` / `setSettings({...})` | 設定の読み書き |

**ネイティブ → JS** (`WebMessagePort`): ブロック (`ArrayBuffer`: float32 の L/R)、状態の変化。1 ブロック約 16KB × 約 23 回/秒 ≈ 0.4MB/s (M0 で詰まらないか測る。詰まるならピークとスコープ用の間引いた点だけ送る)

**設定の持ち主はネイティブ**: 入力元・形式・保存先フォルダ・左右の入れ替え・端末のコピーを残す日数は `SharedPreferences`。JS は橋から読み書きするだけ (`localStorage` と二重に持たない)。**ネイティブ版では隠すもの**: 向きボタン (アプリが横に固定する)、サービスワーカー、OAuth クライアント ID の欄、44.1kHz、「入力の診断」のブラウザ向けの行

**`app.js` の変更 (小さく)**: `openInputNow` / `startRecording` / `stopRecording` / `uploadPending` / `requestToken` に、`WTNative` があれば**ネイティブを呼ぶ枝**を足す。ブラウザの枝は残す。ネイティブの時は、WAV の組み立て・IndexedDB・GIS を使わない

## 5. ステレオ録音の詳細

- **入力元**: 既定 `MIC`。設定で `CAMCORDER` (感度が高く、実測で叩いた音が 0 dBFS まで振れた) を選べる。`UNPROCESSED` / `VOICE_*` は 1 個のマイクだけなので出さない
- **エフェクトを切る**: 録音のセッションに `AutomaticGainControl` / `NoiseSuppressor` / `AcousticEchoCanceler` があれば無効にする (効果音素材に自動音量調整は致命的)。無効にできたかを `open()` の戻りと WAV のメタデータに残す。端末側の処理がそれでも掛かっているかは M0 で測る (実測で片方の録音の低域の左右差が -19dB あった。手の触れ方か処理の差かは未確定)
- **形式**: 48kHz 固定 (端末のマイクは 48kHz で動いていて、44.1kHz は端末内で変換されるだけ)。取り込みは float32 ステレオ
- **書き出し**: 既定は 24bit WAV (PC 側の整音チェーンと形式をそろえる)。**中身は 16bit 精度**と明記 (メタデータにも)。16bit で書き出す時は**ディザを掛けない** (元が正確に 16bit なので、そのまま書けば無損失。ディザはノイズを足すだけ)。ただし実際の値が 16bit の格子に乗っていない場合 (将来の端末) だけディザを使う (ブロックごとに検査)
- **左右の割り当て**: スマホを横にした時にマイクが左右になる。**横画面に固定** (`sensorLandscape`)。画面の回転 (`ROTATION_90` / `ROTATION_270`) で 2 チャンネルを入れ替え、どちらの向きでも左が左になるようにする。どちらがどちらかは**端末ごとの校正値** (S21 は M0 で確定。設定の「左右を入れ替える」で手動も可)。録音の途中で向きが変わっても割り当ては変えない (ファイル内で左右が入れ替わるのを避ける)
- **モノラル**: 左右を混ぜない。14cm 離れた 2 個のマイクを足すと、時間差で特定の周波数が打ち消し合う (横からの音で 1.2kHz 付近)。モノラルは下端のマイク 1 個だけを使う
- **相関メーターの意味**: 間隔のあるマイク (AB 方式) は、もともと左右の相関が低く出る (実測 0.1〜0.3)。ネイティブ版では「左右が同一でないか」の確認用として説明する (広がりの目安としては使いにくい)
- **前面サービス**: `foregroundServiceType="microphone"`、通知 (録音中・経過時間・停止ボタン)、部分的なウェイクロック。画面を消しても録音が続く。Android 14 以降の要件 (`FOREGROUND_SERVICE_MICROPHONE`、通知の許可) を満たす。サービスは画面からの操作で開始 (Android 15 の制限に当たらない)。録音していないレベル確認中は、アプリが裏に回ったらマイクを閉じる (電池とマイク使用中の表示)
- **壊れにくさ**: WAV は録音中 1 秒ごとにヘッダーの長さを更新し、ファイルを同期する (`FileChannel.force`)。アプリが落ちても、次の起動で途中までの WAV を直して「回復した録音」として履歴に出す
- **長時間の録音**: 1 時間または 2GB で自動的に次のファイルに分ける (WAV の 4GB 上限は 24bit ステレオで約 4 時間。PC の取り込みは RF64 / 4GB 超を拒否する)
- **無音の録音は保存しない** (ブラウザ版と同じ: 最大ピーク 1e-6 以下)。数値でない値は 0 にして数える
- **メタデータ**: WAV に、端末名・入力元・マイク配置 (AB 約 14cm)・左右の割り当て・エフェクトの状態・「中身は 16bit 精度」を書く。形は INFO (コメント) を基本にし、PC 側の `wtag` チャンク (schema 1 はサイクル用) に載せるかは PC 側と合わせて決める
- **ファイルの置き場所**: アプリ専用の領域 (`filesDir/rec/`)。送信成功後も既定 7 日は端末に残す (設定で変更可)。「`Download/WaveTagger/` にもコピー」を設定に用意 (聴き返し用)

## 6. Google Drive への送信

- Android 用の OAuth クライアント (種類: Android、パッケージ `jp.wavetagger.rec`、署名鍵の SHA-1) を Google Cloud に 1 つ作る。**デバッグ署名鍵の SHA-1: `94:99:21:6B:1A:D8:8F:1E:CA:05:91:6A:3A:A5:0C:39:2A:1D:C1:EA`** (このアプリを入れる時の署名鍵。鍵を変えると作り直し)
- 認可は Google Play 開発者サービスの `AuthorizationClient` (範囲: `drive`、今の Web 版と同じ。Inbox の既存フォルダに書くため `drive.file` では足りない)。**初回だけ同意画面**が出て、以降は**画面なしでアクセストークンを更新**する
- 送信は WorkManager (ネットワークがある時だけ、失敗は自動で再試行、アプリが閉じても続く)。方式は Web 版と同じ Drive の再開可能アップロード (`uploadType=resumable`、親フォルダ = 設定のフォルダ ID)
- **裏で動く送信は同意画面を出せない**: 同意が必要になったら (期限切れ・取り消し) 送信を止め、通知で「Google への接続が必要です」と知らせる。アプリを開いて接続帯を押すと同意画面
- **注意 (Google 側の制約)**: OAuth 同意画面が「テスト」の状態だと、制限付きの範囲 (`drive`) の同意は**約 7 日で切れる**ことがある。週 1 回の再同意が許容できなければ、公開状態を「本番」(未確認アプリ、100 人まで、警告が出る) にする。**Cloud コンソールでの操作と判断が要る**
- **別の送り方 (検討した案)**: (a) 同期アプリ (FolderSync など) に任せる: 認証も期限切れもこのアプリの外になるが、他社アプリに依存する。(b) 家の Wi-Fi で直接 PC へ送る: 速くて確実だが外出先では送れない。**推奨は Drive API** (外出先でも送れ、Inbox の仕組みをそのまま使える)
- Android の認可が整うまでの間も、録音と WAV の保存・履歴は使える (送信待ちのまま)

## 7. 実装の段階と確認

| 段階 | 内容 | 確認 |
|---|---|---|
| **M0 (測定)** | `StereoTest` に足して測る: エフェクトを無効にできるか、音量を段階的に変えた試験音でゲインが一定か (自動音量調整が無いか)、左右の向き (下端を叩いた時に動くチャンネル)、WebView へのブロックの受け渡し (0.4MB/s) が詰まらないか | 実機。**結果次第で §5 / §4 を直す** |
| **M1** | シェル (WebView + 画面の配信 + 移動の禁止 + 回転で作り直さない) + 橋の骨組み + `MIC` ステレオ取り込み → ブロックを JS へ → メーター・LUFS・スコープ・相関が動く。向きによる左右の入れ替え | PC: エミュレーター (Android 34 の x86_64 イメージが入っている) で画面と橋。実機: ステレオのスコープと、どちらの向きでも左が左 |
| **M2** | 録音 (24bit/16bit WAV・ディザの判定・無音判定・1 秒ごとのヘッダー更新と回復・自動分割・メタデータ)、録音全体の値 (ピーク・Integrated) をネイティブで、前面サービス、履歴 | 実機: 画面を消して録音、WAV を PC で検査 (ヘッダー・時間差の再分析)、アプリを強制終了して回復 |
| **M3** | Google 認可 + WorkManager の送信 + 同意切れの通知 | 実機: 実 Drive へ送信 → PC の Inbox が取り込む (**Cloud コンソールの設定が必要**) |
| **M4** | 設定・隠す項目の整理、`docs/SETUP.md` と `CLAUDE.md`、APK の置き場所 | 実機での通し |

- **自動で確認できること**: WAV の書き込み・16bit の判定・ディザ・ヘッダーの更新・回復・分割・左右の入れ替え・Integrated LUFS (Kotlin に移した `loudness.js` を、`Tools/test_loudness.js` と同じ期待値で突き合わせる) は、JVM の単体テストで確認する。画面と橋はエミュレーターで確認する
- **実機でしか分からないこと**: ステレオの質、左右の向き、画面オフでの録音の継続、実 Drive、通知と許可の挙動。各段階の終わりで APK を渡して確認してもらう

## 8. リスクと未確定

- 左右の割り当て (どちらが L か) は M0 で確定する
- `MIC` と `CAMCORDER` のどちらが録音に向くかは、実際の音 (環境音・距離のある音) で聴いて決める。既定は `MIC`
- 端末側の処理 (自動音量調整・ノイズ抑制・低域の処理) が API で切れない場合がある。M0 で掛かっていると分かったら、他の入力元を探すか、ステレオを諦めて外付けマイク前提にする
- ブロックの受け渡しが WebView で詰まる場合は、送る中身を減らす (§4)
- Google Play 開発者サービスが無い端末では Drive の認可が使えない (S21 は問題なし)
- 配布は自分のスマホへ APK を入れる形 (署名はデバッグ鍵)。ストア公開はしない

## 9. 決めてほしいこと (推奨つき)

1. **送信後の端末のコピー**: 送信成功から 7 日残す (推奨) / すぐ消す / ずっと残す
2. **OAuth の公開状態**: 週 1 回の再同意でよいか、「本番」にして警告を許容するか (M3 の前までに)
3. **縦画面**: 録音は横画面に固定する (推奨。縦では左右にならない)
